# Deployment guide

This guide describes how to deploy BraillePay to **MongoDB Atlas** (database), **Render** (API) and **Vercel** (static frontend). It is written for a first deployment. Changing an existing live deployment should be done deliberately, after review, with a rollback plan.

> **This build has not been deployed by the author.** The live Vercel and Render services were not modified.

Never paste a database URL, API key, webhook secret or JWT secret into chat, issues, or source files. Enter them only in the host's environment-variable settings.

## 0. Before you start

- Decide the public frontend URL, for example `https://your-app.vercel.app`. Every setting below must match it exactly.
- Keep `DEMO_MODE=true` for the demo. Demo users use a shared PIN, so this is not production authentication (see `SECURITY_AUDIT.md`).
- Keep `RAZORPAY_ENABLED=false` until test-mode setup is approved (see `RAZORPAY.md`).

## 1. MongoDB Atlas

1. Create a free M0 cluster.
2. Create a database user with a generated password. Give it read/write access to the `braillepay` database only.
3. Under network access, allow the connection from Render. Check Render's current documentation for its outbound IP addresses. Free-tier outbound IPs may not be fixed, in which case allowlisting may not be practical. Confirm this before you rely on an allowlist.
4. Copy the connection string. You will enter it in Render as `MONGO_URL` in step 2. Replace the password placeholder with the database user's password.

## 2. Render (API)

1. In Render, choose **New → Blueprint** and select this repository. Render reads `render.yaml` at the repository root.
2. When prompted, enter the values marked `sync: false`:
   - `MONGO_URL` (from step 1)
   - `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET` (leave empty until test mode is approved)
3. `JWT_SECRET` is generated by Render (`generateValue: true`). It is not in the repository.
4. Update these to match your frontend URL, then deploy:
   - `CORS_ORIGINS`, `WEBAUTHN_ORIGINS` (full origin, for example `https://your-app.vercel.app`)
   - `WEBAUTHN_RP_ID` (bare domain, for example `your-app.vercel.app`, with no scheme and no port)
5. Check the health endpoint: `https://<render-host>/health` should return a success status.
6. **Seed the demo data.** Startup only creates indexes. It does not seed. Options:
   - With `DEMO_MODE=true`, call `POST https://<render-host>/api/demo/reset`. This runs the same seeding function as `seed.py`. Confirm this on your deployment before relying on it. Note that while `DEMO_MODE=true` this endpoint needs no login, so anyone who can reach the API can reset the demo data. With `DEMO_MODE=false` it returns 404.
   - Or run `python backend/seed.py` on your own machine with a local `backend/.env` that points `MONGO_URL` at Atlas. Do not commit that file.

### Cold starts

Render's free tier sleeps when idle. The first request after a sleep can be slow. The frontend shows a banner saying the server is not responding and may be waking up. It retries reads with backoff and offers a manual **Retry now** button. Payment writes are never retried automatically, because a retry could repeat a payment. If a write times out, the app says the status is unknown and asks the user to check transaction history.

## 3. Vercel (frontend)

1. Import the repository in Vercel as a static site. No build step is needed. The root directory is the repository root.
2. `vercel.json` sets the security headers and the Content Security Policy.
3. `config.js` chooses the API host by hostname. Production builds call `https://braillepay.onrender.com`. **If your Render service has a different hostname, change `config.js` and `connect-src` in `vercel.json` together.** If they differ, the browser blocks the API calls.
4. Open the site and check the browser console for CSP errors.

## 4. Keeping the settings consistent

| Setting | Where | Must equal |
|---|---|---|
| Frontend origin | Render `CORS_ORIGINS`, `WEBAUTHN_ORIGINS` | the Vercel URL, scheme included, no trailing slash |
| WebAuthn RP ID | Render `WEBAUTHN_RP_ID` | the Vercel host, no scheme |
| API host | `config.js` | the Render URL |
| API host in CSP | `vercel.json` `connect-src` | the Render URL |

WebAuthn requires HTTPS outside `localhost`. A mismatch fails for users without a clear message, so check it first when passkey sign-in does not work.

## 5. Updating the service worker

`service-worker.js` caches only the static shell. When you change any shell file (`index.html`, `js/`, `vendor/`, `manifest.json`), increase `CACHE_VERSION` so returning users receive the new files.

## 6. Rollback

- Render: redeploy the previous successful deploy from the service's deploy history.
- Vercel: promote the previous deployment.
- Database: Atlas does not roll back data automatically. Take a snapshot before a change that touches data.

## 7. Before going to production

- [ ] Replace the insecure default JWT behaviour (see `SECURITY_AUDIT.md`, open risks).
- [ ] Run the backend tests against a real MongoDB (see `TESTING.md`).
- [ ] Run `pip-audit` and `npm audit`.
- [ ] Add rate limiting beyond login.
- [ ] Test WebAuthn on real devices.
- [ ] Test the scanner on real phones with real cameras.
- [ ] Get legal and compliance review before any real-money feature (see `P2P_AND_COMPLIANCE.md`).
